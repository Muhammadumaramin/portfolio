Did sales grow, or did your SQL join multiply them?

A practical SQL and Power BI guide to detecting duplicated sales, matching table grain, and reconciling totals before trusting an e-commerce dashboard.

Start with a reconciliation, not a celebration.

The refreshed dashboard shows a sharp increase in sales. Orders look steady, pricing has barely moved, and the warehouse has not shipped more products. Before explaining the improvement as a successful campaign, ask a less exciting question: did a new join repeat the same sales records?

This is a practical risk when marketplace order lines, selling fees, and fulfillment events are combined. Each source can be correct on its own while the combined table is wrong for the measure being summed. A polished dashboard will not reveal that automatically.

My approach is to establish a trusted source total, inspect what one row represents, and test the transformation before interpreting the business result. This article develops the data-grain issue introduced in the earlier dashboard guide into a worked SQL example. All orders and amounts below are illustrative, not employer records or measured results.

Write down what one row represents.

Grain is the meaning of a single row. In a sales-lines table, a row might represent one product line within an order. In a fee-events table, it might represent one fee transaction. Both tables can contain the same order identifier several times for entirely legitimate reasons.

That is different from duplicate ingestion. Two fee events are not duplicates simply because they belong to one order. Preserve event identifiers and distinguish repeated source records from multiple genuine events. Otherwise, an attempted cleanup may remove valid costs.

For every input, record its key, grain, amount definition, currency, and relevant date. Decide whether the report measures ordered sales, shipped sales, payments, or settlements. These are different questions. A join cannot make them interchangeable, and a payment total is not automatically the appropriate revenue benchmark.

Microsoft’s Power BI guidance recommends a consistent grain within fact tables. [1] Use that as a design check: can you describe every row in the table with the same sentence?

See how a valid join produces an invalid total.

Consider one hypothetical order, O-101. It has two sales lines worth $60 and $40, plus two fee events worth $8 and $2. The source totals are therefore $100 in sales and $10 in fees. Assume these are the complete inputs for this example, in one currency.

Join the tables using only order_id. Each sales line matches both fee events. PostgreSQL documents this matching behavior: an inner join returns a row for each right-side match to a left-side row. [2]

Summing these four rows reports $200 in sales and $20 in fees. Both amounts doubled. Even the fee-to-sales ratio remains 10%, so a plausible ratio would not expose the problem. The SQL engine followed the requested relationship; the reporting logic failed to preserve the measures.

Changing the operation to a left join does not stop multiple matches. It preserves unmatched left-side rows, but matching rows can still multiply. Nor does counting distinct orders repair a duplicated sales sum: one correct order count can sit beside an incorrect dollar total.

Aggregate to the reporting grain before combining.

If the desired output is one row per order, summarize each source to that level first. Then combine the summaries. The following illustrative SQL assumes order_id is globally unique, line_amount is the agreed sales measure, and fee_amount uses a consistent sign convention.

WITH sales_by_order AS (
  SELECT order_id, SUM(line_amount) AS sales
  FROM sales_lines
  GROUP BY order_id
), fees_by_order AS (
  SELECT order_id, SUM(fee_amount) AS fees
  FROM fee_events
  GROUP BY order_id
)
SELECT s.order_id, s.sales,
       COALESCE(f.fees, 0) AS fees
FROM sales_by_order s
LEFT JOIN fees_by_order f
  ON s.order_id = f.order_id;

The result for O-101 is one row with $100 in sales and $10 in fees. This preserves both totals for this order-level view. In a multichannel dataset, include channel, account, or other necessary identifiers in both grouping and joining keys when order numbers can repeat.

The zero replacement is an explicit assumption: it is appropriate only when a missing fee row means no fee in a complete extract. If fees arrive later or an export is incomplete, preserve an “unknown” or “pending” status. Also inspect fee-only orders excluded by the sales-led join; they may belong to another period or indicate missing sales data.

Do not use SUM(DISTINCT line_amount) as a general fix. Two legitimate lines can have the same price. Deduplicating monetary values would discard real sales. Repair the relationship or aggregate by the correct business key.

Keep detail when the question needs detail.

An order summary solves an order-level question. It does not establish which product incurred a fee. If the report needs SKU contribution, use genuine line-level links where available. For shared costs, document an allocation rule, identify allocated amounts clearly, and reconcile the allocated total back to the original charge.

In Power BI, consider separate sales and fee fact tables with suitable shared dimensions rather than forcing every event into one wide table. Microsoft generally advises against directly relating two fact tables with many-to-many cardinality and recommends a star-schema approach with dimension tables. [3]

Check the filters users will actually apply. A product filter may affect sales without meaningfully allocating order-level fees. A result can look precise while comparing different populations. If the model cannot support product-level fee attribution, keep the analysis at a supported level or disclose the allocation method.

Dates need the same care. Order date, shipment date, and fee posting date may differ. State which date controls each view. Reconcile an order cohort using its associated events separately from a calendar-period activity report.

Make validation part of every refresh.

Save control totals from the agreed source population before transformation, then compare them with the output using the same filters. A small validation record should include the reporting window, extract timestamp, source row counts, unique keys, currency, and amount totals.

  • Test uniqueness: verify that each table claimed to have one row per order actually does.
  • Count matches: investigate unexpected multiple matches and unmatched keys before publishing.
  • Reconcile amounts: compare sales and fees independently; a stable ratio is insufficient.
  • Exercise edge cases: include multiple lines, equal-priced lines, multiple fees, missing fees, and fee-only orders.
  • Check filtered views: repeat the comparison by channel and date, not just at the grand total.

Agree on a response to failed checks: hold the refreshed report, display a clear data-quality notice, or keep the last verified version with its timestamp. Assign an owner to investigate. A report should not silently replace a trusted total with an unexplained one.

The practical takeaway

Before explaining why sales changed, prove that the transformation preserved sales. A correct total and a clear definition are the foundation of a useful business decision.
